# TLS 101 — making the proxy trust an https Open WebUI

Everything here was measured against this proxy, not recalled. If you landed here from a
502, start at [The error](#the-error). If the certificate checks out and the upstream still
refuses everything, skip to [the gateway wants a
cookie](#when-it-is-not-the-certificate-the-gateway-wants-a-cookie).

## How verification works, in one paragraph

The proxy opens a TLS connection to `LLM_HOSTNAME` and the server sends its certificate —
usually with the certificates above it, up to but not including a root. The proxy then tries
to build a path from what it was sent to something in its **trust store**. The image ships
the public root store (`ca-certificates-bundle`), so a certificate from a public CA verifies
with nothing configured. Every failure below is the same failure: the path could not be
built, because a link is missing from *both* what the server sent and what the container
trusts.

Two details do most of the damage:

- **The container's trust store is not your host's.** A certificate your browser and your
  shell accept can still be untrusted inside the container, and usually is, because an
  internal CA gets installed on hosts, not in images.
- **Anything in the trust store is an anchor.** It does not have to be a root. Trusting the
  issuing CA directly is enough, and is often the whole fix.

## The error

```json
{"detail": "Open WebUI certificate not trusted at https://HOST:443: [SSL:
 CERTIFICATE_VERIFY_FAILED] certificate verify failed: unable to get local issuer
 certificate ..."}
```

One message, **two faults, different fixes**:

| Fault | What fixes it |
| --- | --- |
| The certificate is signed by a CA the container does not have — internal, company, self-signed | Trust that CA |
| The server sends only its own certificate and not the intermediate above it | Trust the **intermediate**. A root alone does not bridge the gap |

The second is common behind a reverse proxy, and it is why "just trust your root CA" can
leave the error byte-for-byte unchanged. Measured, with a test PKI of root → intermediate →
leaf and a server sending only the leaf:

| `UPSTREAM_CA_FILE` holds | Result |
| --- | --- |
| nothing | `unable to get local issuer certificate` |
| the root only | **the identical error** |
| the intermediate only | verifies |
| the intermediate + root | verifies |

So do not guess which fault you have. Ask.

## Diagnose

```bash
./init.sh --tls
```

It prints the chain the server actually sends, says whether it verifies, and names the
certificate that would complete it — with the URL that certificate is published at, when
the certificate carries one:

```
https://ai.example.com:443 sends 1 certificate(s):
  0. ai.example.com
     issued by Example Issuing CA

NOT trusted: unable to get local issuer certificate
the server sent only its own certificate, so nothing links it to a root.
the chain stops at 'ai.example.com', and its issuer 'Example Issuing CA' is not in this trust store.
get the certificate for 'Example Issuing CA' -- and any above it, up to the root --
  it is usually published at http://pki.example.com/issuing-ca.crt
put them all in one PEM file and set UPSTREAM_CA_FILE to it.
```

It runs **inside the container** whenever one is up, because the trust store that decides is
the container's. It then searches **this host** for the missing certificate, and
handshake-tests each candidate it finds rather than recommending one on the strength of its
name:

```
looking for that certificate on this host:
  this host already trusts 'Example Issuing CA'. It is in:
    /usr/local/share/ca-certificates/example-issuing.crt
  verified: 1 of them completes the chain to https://ai.example.com:443:
    /usr/local/share/ca-certificates/example-issuing.crt
  the container does not have it, so hand it one of those -- in .env:
    UPSTREAM_CA_FILE=/usr/local/share/ca-certificates/example-issuing.crt
```

That is the common happy ending: the file is already on the host, and the container just
needs to be handed it. The same two checks are available directly:

```bash
python3 proxy.py --tls-check      # the chain, and why it does or does not verify
python3 proxy.py --find-ca        # search this machine for the missing certificate
python3 proxy.py --autocert DIR   # fetch it into DIR and prove it works
```

`--tls-check` honours `LLM_HOSTNAME`, `UPSTREAM_CA_BUNDLE` and `UPSTREAM_TLS_VERIFY`, so you
can try a candidate file against any host without touching `.env`. `--find-ca` needs only
`LLM_HOSTNAME`: it goes looking for what is missing and tests what it finds.

## Get the certificate

```bash
./init.sh --autocert
```

One command for the whole job. It looks in the two places the certificate can be, cheapest
first — **this host's trust store**, then the **PKI the certificate itself points at** via
its `Authority Information Access` URL — keeps what it finds in `proxy_stack_certs/`, and
only keeps it if it actually verifies the upstream. A file that fixes nothing is worse than
no file, because it looks like the problem is solved.

```
==> Fetching the certificate this upstream needs
    https://ai.example.com:443 needs 'Example Issuing CA', which is not in the container's trust store.
    not on this machine either; following the certificate's own AIA:
      fetching http://pki.example.com/issuing-ca.crt
      got Example Issuing CA

    verified: 1 certificate(s) in /srv/proxy_stack_certs/ai.example.com.pem complete the chain
    UPSTREAM_CA_FILE=/srv/proxy_stack_certs/ai.example.com.pem
    ok   UPSTREAM_CA_FILE written to .env
    ok   UPSTREAM_TLS_VERIFY back to true — the escape hatch is not needed now

==> Applying it
    ok   upstream certificate trusted
```

It then edits `.env`, recreates the container and re-checks from inside it, so a run that
ends `ok upstream certificate trusted` is finished — nothing left to paste. Run it again any
time; when the chain already verifies it says `nothing to fetch` and changes nothing.

Where things land:

| | |
| --- | --- |
| `proxy_stack_certs/<host>.pem` | the certificate(s), one file per upstream (`<host>_<port>.pem` when the port is not 443) |
| `.env` | `UPSTREAM_CA_FILE` set to that path; `UPSTREAM_TLS_VERIFY` put back to `true` if it was off |

The directory sits **beside** `proxy_stack/`, not inside it: these are host state, and nothing
in the image's build context should carry them.

It gives up, without writing a file, when the certificate is on neither source — a PKI that
publishes no AIA URL, or an issuer whose own issuer is missing too. Then you need it from
whoever runs the CA, and the rest of this section is how to do that by hand.

### By hand

The certificate says where its issuer lives — that is what `Authority Information Access` is
for.

```bash
HOST=your-webui.internal
PORT=443
DIR=~/webui-ca; mkdir -p "$DIR"; cd "$DIR"

# 1. the certificate the server presents, and who signed it
openssl s_client -connect $HOST:$PORT -servername $HOST </dev/null 2>/dev/null |
  openssl x509 -out leaf.pem
[ -s leaf.pem ] || echo "no certificate came back from $HOST:$PORT"
openssl x509 -in leaf.pem -noout -subject -issuer -ext authorityInfoAccess

# 2. follow "CA Issuers" upward, whatever format the PKI publishes
: > chain.pem; cp leaf.pem cur.pem; hop=0
while url=$(openssl x509 -in cur.pem -noout -ext authorityInfoAccess 2>/dev/null |
            sed -n 's#.*CA Issuers - URI:##p' | head -1); [ -n "$url" ] && [ $hop -lt 5 ]; do
  hop=$((hop+1)); echo "fetching $url"
  curl -fsSL "$url" -o raw.bin || break
  openssl x509 -inform DER -in raw.bin -out cur.pem 2>/dev/null ||
  openssl x509 -in raw.bin -out cur.pem 2>/dev/null ||
  openssl pkcs7 -inform DER -in raw.bin -print_certs -out cur.pem 2>/dev/null ||
  openssl pkcs7 -in raw.bin -print_certs -out cur.pem 2>/dev/null || break
  cat cur.pem >> chain.pem
  s=$(openssl x509 -in cur.pem -noout -subject); i=$(openssl x509 -in cur.pem -noout -issuer)
  echo "  got ${s#subject=}"
  [ "${s#subject=}" = "${i#issuer=}" ] && break     # self-signed: that is the root
done
if [ -s chain.pem ]; then openssl crl2pkcs7 -nocrl -certfile chain.pem | openssl pkcs7 -print_certs -noout
else echo "this certificate publishes no CA Issuers URL — ask whoever runs the CA"; fi

# 3. prove it fixes the proxy before changing anything
cd /path/to/proxy_stack
UPSTREAM_CA_BUNDLE="$DIR/chain.pem" LLM_HOSTNAME=https://$HOST:$PORT python3 proxy.py --tls-check
```

Step 3 must end with `trusted (via …/chain.pem)`. The loop stops at the first self-signed
certificate, and after five hops regardless, so a PKI that points at itself cannot spin it.

Three things worth knowing about step 1:

- **`s_client` cannot retrieve what the server does not send.** If the server omits its
  intermediate, `-showcerts` shows you the leaf and nothing else; the AIA fetch in step 2 is
  what actually gets the CA.
- If there is no `Authority Information Access` line, there is nothing to download. Ask
  whoever runs the CA, or export the certificate from a browser that trusts the site
  (padlock → certificate → export each one above the leaf).
- On AD CS, `certutil -ca.cert root.cer` then
  `openssl x509 -inform der -in root.cer -out root.pem` gets you the root directly.

## Wire it in

```bash
# proxy_stack/.env
UPSTREAM_CA_FILE=/home/you/webui-ca/chain.pem   # a path on THIS host
UPSTREAM_TLS_VERIFY=true
```

```bash
./init.sh --no-build     # .env alone does not reach a running container
```

The file is mounted read-only into the container at `/etc/ssl/upstream-ca.pem` and trusted
**in addition to** the public roots, so a mixed estate keeps working — concatenate as many
certificates as the chain needs. With `UPSTREAM_CA_FILE` unset, compose mounts `/dev/null`
there and the image's own store is used untouched.

Bad input fails early and says so: `init.sh` refuses to start if the path does not exist,
and the proxy exits at startup — rather than 502ing on every request — if the file is not
readable PEM.

## The escape hatch

```bash
UPSTREAM_TLS_VERIFY=false
```

Accepts any certificate. It drops the only check that the host answering is the one you
named: anything able to intercept that connection sees the pinned token and every
conversation. Use it to stay unblocked while the CA is in transit, not as the fix.

It is deliberately hard to forget:

| Where | What it says |
| --- | --- |
| Container log, every start | `warning: UPSTREAM_TLS_VERIFY=false -- the upstream certificate is not checked` |
| `GET /health` | `"upstream_tls_verified": false` |
| `./init.sh` | warns on every run |
| `./init.sh --tls` | still reports what verification *would* find, so you can tell when the CA has landed |
| `./test.sh` | asserts the posture matches the scheme, so an https upstream cannot be downgraded unnoticed |

When `--tls-check` reports `trusted`, it says so plainly: the flag is no longer buying you
anything. Remove it and re-run `./init.sh --no-build`.

## When it is not the certificate: the gateway wants a cookie

TLS is not the only thing between the proxy and a remote Open WebUI. Where a deployment puts
an **SSO gateway** in front, that gateway authenticates by **session cookie**, and a request
carrying only `Authorization: Bearer …` is anonymous to it. It refuses before Open WebUI
sees anything:

```json
{"detail": "no session ID found"}
```

The tell is that the TLS side is clean and requests still fail:

| | |
| --- | --- |
| `./init.sh --tls` says `trusted` | the certificate is fine — this is not a TLS problem |
| The 401 arrives instantly, and mentions a session | it came from the gateway, not from Open WebUI |
| A new Open WebUI token changes nothing | the request never reaches the service that would check it |

No Open WebUI token fixes this, because the gateway is refusing first. Give the proxy the
cookie instead, from a browser that is logged in — F12 → Application → Cookies:

```bash
# proxy_stack/.env
UPSTREAM_COOKIE=session=a1b2c3...
```

```bash
./init.sh --no-build
```

It is sent with every upstream request. A caller's own `Cookie` header wins over it, exactly
as a caller's own token wins over `WEBUI_TOKEN`, so a browser-based client keeps its own
identity. `/health` reports `pinned_cookie_configured`, and the startup line says
`pinned cookie: yes`.

When the upstream answers 401 or 403 and no cookie was in play, the proxy says so in its own
log rather than in the response body — the body belongs to the upstream:

```
upstream refused with 401 and no cookie was sent -- if it sits behind an SSO gateway,
that gateway wants a session cookie: set UPSTREAM_COOKIE
```

> A session cookie is as sensitive as a password, and it **expires** — expect to refresh it.
> If the gateway can issue a long-lived API key or exempt service traffic, that is the
> better credential. `.env` is git-ignored; keep it that way.

Upstream refusals are relayed with their own status and body, so what you see is what the
gateway said, not a quoted copy of it.

## Settings

| Setting | Default | Effect |
| --- | --- | --- |
| `UPSTREAM_CA_FILE` | unset | A PEM on the host, mounted into the container and trusted alongside the public roots. `.env` only |
| `UPSTREAM_CA_BUNDLE` | unset | The same file, as the container sees it. Set by compose from `UPSTREAM_CA_FILE`; set it yourself only when running `proxy.py` directly |
| `UPSTREAM_TLS_VERIFY` | `true` | `false` accepts any upstream certificate |
| `UPSTREAM_COOKIE` | unset | A `Cookie` header sent upstream, for an Open WebUI behind a gateway that authenticates by session. Not TLS, but the other reason a remote upstream refuses everything |

Values are stripped of surrounding whitespace and quotes before they are read — a trailing
space on `UPSTREAM_TLS_VERIFY=false ` used to read as `true` and silently keep verifying.

## If it still fails

| Symptom | Cause |
| --- | --- |
| `--autocert` says it cannot obtain the certificate | Neither this host nor the PKI's own AIA URL has it. Ask whoever runs the CA for the full chain |
| Same error after setting `UPSTREAM_CA_FILE` | The container was not recreated. `./init.sh --no-build` |
| Same error, and the file holds the root | The server is omitting its intermediate; that intermediate has to be in the file too |
| `--tls-check` says trusted, requests still 502 | Not TLS. Check `/health`, the token, and `docker compose logs proxy` |
| `--tls-check` says trusted, requests 401 with `no session ID found` | A gateway in front of Open WebUI wants a session cookie — see [above](#when-it-is-not-the-certificate-the-gateway-wants-a-cookie) |
| `Hostname mismatch` | The certificate is not valid for the name in `LLM_HOSTNAME`. Use the name the certificate carries, not an IP |
| `certificate has expired` | Nothing to configure here — the upstream needs renewing |
